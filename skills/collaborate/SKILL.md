# 夥伴協作

多個 agent 同時運作時，優先使用宿主提供的原生協作工具；需要跨 session 聯絡時，才使用環境已安裝且可驗證的 Switchboard、wake-cc 或其他通道。

不要假設任何固定 alias、值班表或常駐 session 存在。先查證可用工具與目標，再決定協作方式。

## 什麼時候需要協作

- 手上有任務適合交給另一個正在線上的agent
- 收到其他agent的委派請求
- 發現自己在做的事情跟另一個agent有關
- 需要其他agent的專長或正在使用的資源

## 上線流程

新 session 啟動時：

1. **盤點能力**：確認宿主有哪些原生子代理或跨 session 工具
2. **確認目標**：以工具或現有狀態來源查證目標存在
3. **建立回報契約**：說明產出、限制與回覆方式
4. **避免廣播**：除非使用者明確要求，不向無關 session 發訊息

## 委派任務

### 什麼時候委派

- 任務不在自己的專長範圍，但有其他agent正在做相關的事
- 需要平行處理多件事，自己忙不過來
- 任務需要特定資源（如 Chrome MCP），而那個資源在別的 session 手上

### 怎麼寫委派訊息

好的委派訊息包含：

1. **任務描述**：要做什麼，一兩句話
2. **期望產出**：做完後要交付什麼
3. **參考資料**：相關檔案的路徑（不要把內容貼過去，浪費 token）
4. **完成後回報**：做完通知誰、更新什麼紀錄

範例：
```
請幫我為 issue #1234 起草一份技術選型 ADR：評估快取方案 Redis 與 Memcached 的取捨。
期望產出：ADR 草稿，包含選項評估（功能/成本/相容性）、決策、後果。
參考資料：issue #1234 的需求討論串
完成後：結果 send 回給我（`main`），
同時在團隊知識庫對應資料夾建立該 ADR 文件。
```

> **知識庫上載判準**：需要團隊人類成員 review 才能動、或未來會回頭看的文件，才寫到團隊知識庫（路徑慣例：`<團隊>/<專案>/#{issueid}{主旨}/`）。型別檢查報告、debug log 等 transient 結果不需要上知識庫，留在本地或當下回報即可。

### 不好的委派

- 「幫我看一下 issue #1234」— 太模糊，不知道要看什麼
- 把整份檔案內容貼在協作訊息裡 — 浪費 token，給路徑就好
- 沒有說完成後怎麼處理 — 做完了但沒人知道

## 回報結果

收到委派並完成後：

1. **回覆委派者**：使用原委派通道回報結果摘要
2. **更新紀錄**：如果委派訊息指定了要更新的檔案，更新它
3. **更新共享狀態**：只有委派契約指定狀態檔，而且該檔案確實存在時才更新

## 主動建議（不是直接修改）

如果你在做的事情發現了對其他agent有用的資訊：

- **給建議，不直接改檔案**：透過原委派通道告訴對方，讓對方決定怎麼處理
- **原因**：避免同一個檔案被多個 session 同時修改
- **例外**：值班表自己的條目可以直接改

## 值班表維護

若環境使用 `SWITCHBOARD_STATUS.md`，把它視為值班通訊錄而非進度追蹤；檔案不存在時略過本節。

**記錄什麼**：
- 誰在線上
- 每個 session 負責什麼
- 怎麼聯繫（工具 target、alias 或 session id）

**不記錄什麼**：
- 任務進度（進度放在任務自己的地方）
- 詳細的工作日誌

**更新時機**：
- 上線時：加自己
- 任務變更時：更新自己的條目
- 收到新同伴廣播時：讀值班表更新全域資訊
- 下線時：廣播告別

## 下線流程

session 結束時：

1. **廣播告別**：告訴大家自己要下線了
2. **交接未完成任務**：如果有未完成的事情，說明狀態並建議接手方式
3. **值班表更新**：（由收到告別廣播的其他 session 負責清除）

## 通訊紀律

- 協作訊息要簡潔，不要長篇大論
- 參考資料給路徑不給內容
- 不要在工作通道閒聊
- 未經使用者授權，不把私人資訊、憑證或公司機密轉傳到其他 session
