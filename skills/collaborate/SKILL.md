# 夥伴協作

多個agent session 同時運作時，透過 switchboard 協作的規範。

核心觀念：switchboard 是同一個人的腦內對話頻道。每個 session 是同一個agent的不同分身，不是不同的人。

## 什麼時候需要協作

- 手上有任務適合交給另一個正在線上的agent
- 收到其他agent的委派請求
- 發現自己在做的事情跟另一個agent有關
- 需要其他agent的專長或正在使用的資源

## 上線流程

新 session 啟動時：

1. **註冊 switchboard**：取一個好懂的名字（`line`、`batch`）
2. **設定 Monitor**：訂閱 inbox stream，確保能收到訊息
3. **讀值班表**：看 `SWITCHBOARD_STATUS.md` 了解誰在線上
4. **廣播介紹**：告訴大家自己是誰、今天要做什麼

## 委派任務

### 什麼時候委派

- 任務不在自己的專長範圍，但有其他agent正在做相關的事
- 需要平行處理多件事，自己忙不過來
- 任務需要特定資源（如 Chrome MCP），而那個資源在別的 session 手上

### 怎麼寫委派訊息

好的委派訊息包含：

1. **任務描述**：要做什麼，一兩句話
2. **期望產出**：做完後要交付什麼
3. **參考資料**：相關檔案的路徑（不要把內容貼過去，浪費 token）
4. **完成後回報**：做完通知誰、更新什麼紀錄

範例：
```
請幫我為 issue #1234 起草一份技術選型 ADR：評估快取方案 Redis 與 Memcached 的取捨。
期望產出：ADR 草稿，包含選項評估（功能/成本/相容性）、決策、後果。
參考資料：issue #1234 的需求討論串
完成後：結果 send 回給我（`main`），
同時在團隊知識庫對應資料夾建立該 ADR 文件。
```

> **知識庫上載判準**：需要團隊人類成員 review 才能動、或未來會回頭看的文件，才寫到團隊知識庫（路徑慣例：`<團隊>/<專案>/#{issueid}{主旨}/`）。型別檢查報告、debug log 等 transient 結果不需要上知識庫，留在本地或當下回報即可。

### 不好的委派

- 「幫我看一下 issue #1234」— 太模糊，不知道要看什麼
- 把整份檔案內容貼在 switchboard 訊息裡 — 浪費 token，給路徑就好
- 沒有說完成後怎麼處理 — 做完了但沒人知道

## 回報結果

收到委派並完成後：

1. **回覆委派者**：用 switchboard send 回報結果摘要
2. **更新紀錄**：如果委派訊息指定了要更新的檔案，更新它
3. **更新值班表**：如果任務改變了自己的狀態，更新 SWITCHBOARD_STATUS.md 裡自己的條目

## 主動建議（不是直接修改）

如果你在做的事情發現了對其他agent有用的資訊：

- **給建議，不直接改檔案**：透過 switchboard 告訴對方，讓對方決定怎麼處理
- **原因**：避免同一個檔案被多個 session 同時修改
- **例外**：值班表自己的條目可以直接改

## 值班表維護

`SWITCHBOARD_STATUS.md` 是值班通訊錄，不是進度追蹤。

**記錄什麼**：
- 誰在線上
- 每個 session 負責什麼
- 怎麼聯繫（switchboard alias）

**不記錄什麼**：
- 任務進度（進度放在任務自己的地方）
- 詳細的工作日誌

**更新時機**：
- 上線時：加自己
- 任務變更時：更新自己的條目
- 收到新同伴廣播時：讀值班表更新全域資訊
- 下線時：廣播告別

## 下線流程

session 結束時：

1. **廣播告別**：告訴大家自己要下線了
2. **交接未完成任務**：如果有未完成的事情，說明狀態並建議接手方式
3. **值班表更新**：（由收到告別廣播的其他 session 負責清除）

## 通訊紀律

- switchboard 訊息要簡潔，不要長篇大論
- 參考資料給路徑不給內容
- 不要在 switchboard 上閒聊——它是工作頻道
- 涉及使用者的私人訊息不透過 switchboard 轉傳
