# 系統排查

## 核心原則

**亂猜浪費時間、還會製造新問題。先找到根本原因，再動手修。**

違反這個流程的字面意義，就是違反排查的精神。

## 鐵律

```
沒有完成根本原因調查，不能提出修正方案。
```

## 什麼時候用

**任何非預期狀況：**
- 測試失敗
- Pipeline 中斷或異常
- 部署失敗
- 算圖結果不符預期
- TTS 發音異常
- 影片合成問題
- 效能問題
- 工具或 MCP 連線異常

**特別是這些時候：**
- 時間壓力大（緊急狀況最容易讓人亂猜）
- 「改一下就好了」看起來很明顯
- 已經試了好幾個修法都不行
- 上一個修法沒用
- 你不完全理解發生了什麼

## 四個階段

必須依序完成每個階段。

### 階段一：根本原因調查

**在嘗試任何修正之前：**

1. **仔細讀錯誤訊息**
   - 不要跳過錯誤和警告
   - 讀完整個 stack trace / log
   - 記下行號、檔案路徑、錯誤碼
   - 錯誤訊息通常就包含答案

2. **穩定重現**
   - 能可靠地觸發嗎？
   - 精確的步驟是什麼？
   - 每次都會發生嗎？
   - 不能重現 → 蒐集更多資料，不要猜

3. **檢查近期變更**
   - 什麼東西變了？
   - git diff、最近的 commit
   - 新的依賴、設定變更
   - 環境差異

4. **多層系統：在每層邊界蒐集證據**

   系統有多個元件（pipeline → docker → API → 檔案系統）時：

   ```
   對每個元件邊界：
     - 記錄進入元件的資料
     - 記錄離開元件的資料
     - 檢查環境/設定是否正確傳遞
     - 確認每一層的狀態

   跑一次蒐集證據 → 分析哪一層壞了 → 調查那一層
   ```

5. **追蹤資料流**
   - 錯誤的值從哪裡來？
   - 誰用錯誤的值呼叫了這裡？
   - 一路往上追到源頭
   - 在源頭修，不在症狀修

### 階段二：模式分析

1. **找到正常運作的案例**
   - 同系統中類似但正常的東西
   - 什麼東西跟壞的類似但好好的？

2. **逐項比較**
   - 正常和異常之間有什麼不同？
   - 列出每一個差異，不管多小
   - 不要假設「那個不重要」

3. **理解依賴關係**
   - 這個東西需要什麼其他元件？
   - 需要什麼設定、環境、前提？

### 階段三：假設與測試

1. **形成一個假設**
   - 清楚陳述：「我認為根本原因是 X，因為 Y」
   - 寫下來
   - 要具體，不要模糊

2. **最小測試**
   - 做最小的改動來測試假設
   - 一次只改一個變數
   - 不要同時改好幾個東西

3. **驗證**
   - 有效 → 階段四
   - 無效 → 形成新假設
   - 不要在無效的修法上面再堆更多修法

4. **三次失敗規則**
   - 如果連續 3 次修法都失敗 → 停下來，質疑架構
   - 不是假設錯了，是整個做法可能有根本性問題
   - 跟使用者討論再繼續

### 階段四：實作修正

1. **建立失敗的驗證**
   - 能重現問題的測試或步驟
   - 修好之前必須是失敗的
   - 修好之後必須是通過的

2. **實作單一修正**
   - 針對根本原因
   - 一次一個改動
   - 不順手改其他東西

3. **驗證修正**
   - 驗證通過了嗎？
   - 其他東西沒壞嗎？
   - 問題真的解決了嗎？

## 先判斷是不是假性失敗

**在進階段一之前**，先問一句：這真的壞了，還是系統回報的狀態跟實際情形對不上？反射性地把假摔當真、急著重跑/回滾/改 code，是最浪費時間的坑，甚至會把好東西弄壞（把已正常啟動的容器再 rebuild、把只是 lag 的 pipeline 重跑）。已知的假性失敗形狀：

- **啟動 race**：health check 撞冷啟動回 `HTTP 000`／連不上 ≠ 服務壞，可能只是還在起。解法：retry poll 到 200。
- **狀態同步延遲**：log 顯示完成、但平台/DB 要 30 秒到 2 分鐘才同步；MinIO/DB 寫入到可讀有空窗。
- **守門點錯位**：監看的指標跟真正在意的事不是同一件——按鈕狀態、hook 掛的副檔名，都可能不是實際發生變化的地方。設檢查點先問「我真正要防的動作會留下什麼痕跡」，不是「哪裡方便攔」。
- **monitor 推送亂序**：monitor 訊息可能推到 N 分鐘前的舊事件，畫面其實已經在跑下一步——用實際產物（檔案存在、curl 200、log tail）核對，不要只信 monitor 文字。
- **grep 大小寫假失敗**：`grep -c xxx` = 0 不代表沒部署，可能是變數/常數名大小寫不同（`HClip` vs `hclip`）。驗部署一律 `grep -ci` 或用精確常數名。
- **空 glob／空集合假通過**：目錄不存在時 glob 抓 0 檔案，規則扣 0 分變成「乾淨」；`diff` 兩邊都空也會顯示「沒有差異」。**比對或掃描前先確認每一邊都非空**（各印一次筆數），空結果不是「沒問題」的證據，是「沒有證據」。
- **零值的歧義**：`0`／`null`／空集合可能是「測了 N 筆全部失敗」，也可能是「根本沒有東西進來測」——看到 0 先問「分母是多少」，分母為 0 最容易被誤讀成分子為 0。

判斷完是假性失敗 → 用對應方法確認後放行；判斷不是 → 才進入階段一當真實失敗處理。

## 各任務類型的排查要點

### 程式 bug
- 讀 stack trace → 檢查 git diff → 追蹤資料流 → 寫失敗測試 → 修

### Pipeline 中斷
- 讀 docker logs → 找到中斷的階段 → 檢查那個階段的輸入輸出 → 修

### 算圖異常
- 對照 prompt 和結果 → 檢查是否觸發 filter → 檢查模型/LoRA 設定 → 調整 prompt

### TTS 問題
- 聽異常段落 → 檢查腳本文字 → 檢查是否有發音矯正表覆蓋 → 調整

### 部署失敗
- 讀部署 log → 檢查 .env → 進 container 確認環境 → 修

### MCP / 工具問題
- 檢查連線狀態 → 確認 config → 重啟工具 → 如果持續失敗走備援路徑

## 自我欺騙的警訊

| 藉口 | 現實 |
|------|------|
| 「問題很簡單，不需要走流程」 | 簡單問題也有根本原因。流程對簡單問題很快。 |
| 「緊急，沒時間走流程」 | 系統化排查比亂猜快。 |
| 「先改這個試試看」 | 第一個修法會定調。一開始就做對。 |
| 「我看到問題了，讓我修」 | 看到症狀 ≠ 理解根本原因。 |
| 「再試一次就好了」（已經失敗 2 次以上） | 3 次失敗 = 架構問題。別再試了。 |
| 「多改幾個地方一起測省時間」 | 無法隔離哪個有效。會引入新問題。 |

## 紅旗 — 停下來回到階段一

- 「先快速修一下，之後再調查」
- 「改 X 看看會不會好」
- 「同時改好幾個地方，一起跑測試」
- 「跳過測試，我手動確認」
- 「大概是 X 的問題」
- 「我不太確定但這個可能有效」
- 還沒追蹤資料流就提出解決方案
- 連續失敗 3 次還想再試一次

**以上全部代表：停下來，回到階段一。**
