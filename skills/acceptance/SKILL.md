# 驗收標準

## 核心原則

**先定義「怎樣算做好」，再開始做。**

如果你不先定義驗收標準，你就不知道什麼時候該停下來。你會做太多、做太少、或做了但做偏。

**違反這條規則的字面意義，就是違反這條規則的精神。**

## 適用時機

**所有嚴謹任務** — 必須。
**混合任務** — 簡化版：至少列出「做完時我期望看到什麼」。
**創意任務** — 不適用（四不二要就是驗收標準）。

## 通用流程

```
動手之前：
1. 定義：做完時，成功長什麼樣？
2. 確認：現在還沒達到這個狀態（基線確認）
3. 動手
4. 驗證：現在達到了嗎？
5. 達到了才能宣稱完成
```

這就是 TDD 的 Red-Green 循環泛化到所有任務類型。

## 各任務類型的驗收標準

### 程式開發（TDD）

經典的 Red-Green-Refactor：

1. **寫測試**（定義驗收標準）
2. **跑測試確認失敗**（基線確認）
3. **寫最小實作**（動手）
4. **跑測試確認通過**（驗證）
5. **重構**（打磨）

鐵律：**沒有先寫測試就不寫產品程式碼。**

先寫了程式碼？刪掉。從測試重新開始。

- 不要留著「當參考」
- 不要「邊看邊寫測試」
- 不要回頭看
- 刪掉就是刪掉

#### 好的測試

| 品質 | 好 | 壞 |
|------|---|---|
| **最小化** | 測一件事。名稱裡有「和」就該拆 | `test_驗證信箱和網域和空白` |
| **清楚** | 名稱描述行為 | `test_test1` |
| **意圖明確** | 展示期望的 API | 模糊了程式碼該做什麼 |

#### 為什麼順序重要

「先寫完再補測試」的問題：
- 測試立刻就通過了，但通過不代表它測對了東西
- 你會測你寫出來的東西，不是測需求要的東西
- 你會驗證你記得的邊界情況，不是你發現的
- 你從來沒看到測試抓到 bug

### 教學影片

驗收標準 = pattern checklist + 技術品質：

**腳本階段：**
- [ ] TIER 0：不俯視觀眾 → 通過
- [ ] TIER 1 必勝 6 項：每項逐一確認
- [ ] TIER 2 加分 5 項：有多少算多少

**動畫階段：**
- [ ] 每張投影片視覺正確（截圖確認）
- [ ] 互動式圖表使用正確的工具（D3 / JSXGraph 等）
- [ ] 排版符合卡片規範（橫向讀取靠左置中、縱向讀取置中靠上）

**TTS 階段：**
- [ ] 發音正確（特別是專有名詞和數學符號）
- [ ] 斷句自然、語速適中
- [ ] 品質不低於基準（Puck F0）

**合成階段：**
- [ ] 音畫同步
- [ ] 字幕對齊
- [ ] 影片可正常播放

### AI 算圖

驗收標準 = 評圖四面向：

- [ ] **合理性**：視覺元素是否服務於角色的故事
- [ ] **生命感**：角色像活的，不是擺拍的假人
- [ ] **技術面**：色調乾淨、皮膚自然、五官比例正常
- [ ] **細節面**：眼睛清晰、角色可辨識

如果要釋出：
- [ ] 不含社群成員的個資或暱稱（隱私紅線）
- [ ] prompt 沒有觸發 NSFW filter 的關鍵字

### 研究 / 寫作

- [ ] 論點有證據支持
- [ ] 引用來源可查證
- [ ] 目標讀者能理解
- [ ] 沒有邏輯漏洞

### 部署

- [ ] 服務可存取
- [ ] 環境變數正確
- [ ] .env 沒被打包進 tar
- [ ] docker 容器運行正常
- [ ] 備份存在且大小合理

## 自我欺騙的警訊

| 藉口 | 現實 |
|------|------|
| 「太簡單不需要定義驗收標準」 | 簡單的任務更容易因假設而出錯。30 秒就能列好。 |
| 「先做再說」 | 沒定義就不知道什麼時候該停。你會做太多或做偏。 |
| 「做完再補驗收標準」 | 後補的標準會配合你做出來的東西，而不是需求。 |
| 「手動測過了」 | 手動測試是隨機的，不是系統性的。沒有紀錄、不能重跑。 |
| 「之前用過類似的做法」 | 類似 ≠ 相同。每次都要定義。 |
| 「驗收標準會拖慢速度」 | 不定義驗收標準 → debug → 返工 → 更慢。 |

## 紅旗 — 停下來重新開始

- 還沒定義驗收標準就開始動手
- 驗收標準在做完之後才寫
- 做完發現「不確定算不算做好」
- 「就這一次跳過」
- 驗收標準太模糊（「品質要好」不是驗收標準）

## 卡住時

| 問題 | 解法 |
|------|------|
| 不知道怎麼定義驗收標準 | 問使用者「你期望做完時看到什麼？」 |
| 驗收標準太複雜 | 任務太大，拆小。 |
| 不確定標準是否合理 | 列出來讓使用者確認。 |

## 和其他 skill 的關係

- **思考整理**（`brainstorm`）：探索階段可能產出初步驗收標準
- **擬定計畫**（`plan`）：計畫的每個任務都應該有驗證步驟（就是驗收標準的具體化）
- **完成驗證**（`verify`）：用驗收標準來做最後驗證

## 最終規則

```
要做的事 → 先定義驗收標準
驗收標準沒列 → 不能動手
```

沒有使用者的同意，不可以跳過。
