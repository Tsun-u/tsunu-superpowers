# 先看 skill 再動手

skill 是把踩過的坑和定好的做法寫下來的地方。動手前先看一眼清單，因為 skill 會改版，裡面也常有從任務本身看不出來的限制（例如推送前要過哪些檢查）。憑印象做，最常見的結果是照舊版做，或漏掉一條不會報錯的規矩。

## 怎麼判斷

- 清單裡有 skill 的觸發情境跟手上的事對得上：先載入再做，依宿主的 skill 觸發規則使用。
- 不確定對不對得上：載入看看。讀了發現不適用就放下，成本只是一次讀取。
- 明顯無關（閒聊、回答一個單純的事實）：直接回。
- 載入過的 skill，隔了對話壓縮或隔了很久要再用：重讀本體。
- 準備說「做好了」、commit 或交付之前：載入完成驗證（`verify`）。這個時機落在做事的中途，不會有新訊息提醒你回頭看清單，所以寫在這裡。

## 誰說了算

1. 宿主的系統、開發者與安全指令
2. 使用者的明確指示（`AGENTS.md`、`CLAUDE.md` 或當下的要求）
3. 適用的 tsunu-superpowers skill
4. 預設行為

skill 不能覆蓋更高優先級的指令。skill 跟使用者的指示衝突時，照使用者的。例如 `CLAUDE.md` 說「不要用 TDD」而某個 skill 說要，就不用。

## 先後順序

多個 skill 都適用時，先載入決定「怎麼做」的（思考整理 `brainstorm`、系統排查 `debug`），再載入指導具體執行的。

- 「我們來做 X」：先思考整理，再執行。
- 「這裡壞了」：先系統排查，再修。
- 「查一下議題 #1234」：任務明確又有專用 skill，直接用專用的。

## 嚴格與彈性

擬定計畫（`plan`）裡的驗收標準、完成驗證（`verify`）、系統排查（`debug`）是照步驟做的；思考整理（`brainstorm`）、同儕審查（`review`）依情境調整。每份 skill 自己會寫明是哪一種。

## 任務分流

收到任務後用任務分流（`triage`）判斷任務性質和流程要走多完整。已有專用 skill 且任務明確時，直接用專用的，不需要走完整流程。
