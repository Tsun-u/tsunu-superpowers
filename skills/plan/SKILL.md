# 擬定計畫

寫一份詳細的實作計畫，假設執行者對這個專案一無所知。每個步驟都要交代清楚：碰哪些檔案、做什麼、怎麼驗證、預期結果。

## 計畫文件位置

存到：`docs/plans/YYYY-MM-DD-<功能名稱>.md`
（使用者指定位置優先）

## 範圍確認

如果設計涵蓋多個獨立子系統，應該在思考整理（`brainstorm`）階段就拆開了。如果沒有，建議拆成多份計畫——每份計畫獨立產出可驗證的成果。

## 檔案盤點

動手之前，先列出所有會新增或修改的檔案，標明每個檔案的職責。這是分工拆解的基礎。

原則：
- 每個檔案有一個清楚的職責
- 一起變動的檔案放在一起
- 現有專案裡，先遵循既有風格
- 偏好小而聚焦的檔案——方便理解也方便編輯

## 步驟粒度

**每一步是一個動作（2-5 分鐘）：**

程式開發範例：
- 「寫測試」— 一步
- 「跑測試確認失敗」— 一步
- 「寫最小實作讓測試通過」— 一步
- 「跑測試確認通過」— 一步
- 「commit」— 一步

影片製作範例：
- 「撰寫大綱」— 一步
- 「擴展腳本」— 一步
- 「自審腳本品質」— 一步
- 「生成投影片」— 一步
- 「截圖檢查每張投影片」— 一步

算圖範例：
- 「確認 prompt 需求」— 一步
- 「選擇模型和 LoRA」— 一步
- 「生成初版」— 一步
- 「評圖檢查品質」— 一步
- 「調整 prompt 重生」— 一步

## 計畫文件格式

每份計畫必須以這個開頭：

```markdown
# [功能名稱] 實作計畫

> **給執行者：** 使用執行計畫（`execute`）skill 逐步完成此計畫。步驟使用 checkbox（`- [ ]`）格式追蹤進度。

**目標：** [一句話描述這份計畫要做出什麼]

**方法：** [2-3 句話描述做法]

**工具 / 技術：** [會用到的關鍵工具或技術]

---
```

## 任務結構

### 程式開發任務

````markdown
### 任務 N：[元件名稱]

**檔案：**
- 新增：`精確/路徑/檔案.py`
- 修改：`精確/路徑/既有.py:123-145`
- 測試：`tests/精確/路徑/test_檔案.py`

- [ ] **步驟 1：寫測試**

```python
def test_具體行為():
    result = function(input)
    assert result == expected
```

- [ ] **步驟 2：跑測試確認失敗**

執行：`pytest tests/path/test.py::test_name -v`
預期：FAIL，訊息「function not defined」

- [ ] **步驟 3：寫最小實作**

```python
def function(input):
    return expected
```

- [ ] **步驟 4：跑測試確認通過**

執行：`pytest tests/path/test.py::test_name -v`
預期：PASS

- [ ] **步驟 5：commit**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: 新增某功能"
```
````

### 影片製作任務

````markdown
### 任務 N：[階段名稱]

**檔案：**
- 輸入：`精確/路徑/input.json`
- 輸出：`精確/路徑/output/`
- 設定：`精確/路徑/config.py`

- [ ] **步驟 1：觸發 pipeline**

操作：在平台管理頁面點擊「生成此主題」
預期：alert 顯示「成功觸發: 1」

- [ ] **步驟 2：監控進度**

操作：開啟 Monitor 監控 docker logs
預期事件序列：Router → Outline → Script → Consultant → Improve → Review → Pipeline complete

- [ ] **步驟 3：品質自審**

操作：下載輸出檔案，逐一檢查
驗收標準：
- 腳本 pattern checklist 6/6
- 投影片無視覺瑕疵
- TTS 發音正確、斷句自然
````

### 通用任務

````markdown
### 任務 N：[步驟名稱]

**輸入：** [需要什麼才能開始]
**輸出：** [做完會產出什麼]

- [ ] **步驟 1：[動作]**

操作：[具體怎麼做]
預期：[做完會看到什麼]

- [ ] **步驟 2：[驗證]**

操作：[怎麼確認做對了]
預期：[正確的結果長什麼樣]
````

## 禁止佔位符

每一步都必須包含執行者需要的實際內容。以下是**計畫的失敗**——絕對不能寫：

- 「待定」「TODO」「之後再說」「之後補」
- 「加上適當的錯誤處理」「做好驗證」「處理邊界情況」
- 「針對上面的內容寫測試」（沒附測試程式碼）
- 「跟任務 N 類似」（重複寫一遍——執行者可能不按順序讀）
- 只描述「做什麼」但沒有「怎麼做」的步驟
- 引用了沒有在任何任務中定義的型別、函式、方法

## 自審

寫完計畫後，用新的眼光檢查一遍：

1. **設計覆蓋度**：翻一遍設計文件的每個需求，每個都能對應到計畫中的某個任務嗎？列出缺口。
2. **佔位符掃描**：搜尋上面「禁止佔位符」列出的模式。修掉。
3. **一致性**：後面的任務用到的型別、函式名稱跟前面定義的一樣嗎？任務 3 叫 `clearLayers()`、任務 7 叫 `clearFullLayers()` 就是 bug。

有問題直接修，不用重跑自審。如果發現設計有需求但計畫沒涵蓋，補上任務。

## 執行交接

計畫存檔後，提供執行選項：

> **「計畫寫好了，存在 `<路徑>`。兩種執行方式：**
>
> **1. 子代理執行（推薦）** — 每個任務派一個獨立子代理，任務間做 review
>
> **2. 本 session 執行** — 在目前的對話中逐步執行，設定 review 檢查點
>
> **你選哪個？」**

選擇後觸發執行計畫（`execute`）skill。

## 核心提醒

- 精確的檔案路徑
- 每個步驟都附具體內容——程式碼步驟要有程式碼，操作步驟要有操作指令
- 驗證步驟要寫預期輸出
- DRY、YAGNI、先定義驗收標準（`acceptance`）再實作
