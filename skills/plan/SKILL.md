# 擬定計畫

寫一份詳細的實作計畫，假設執行者對這個專案一無所知。每個步驟都要交代清楚：碰哪些檔案、做什麼、怎麼驗證、預期結果。

## 計畫文件位置

存到：`docs/plans/YYYY-MM-DD-<功能名稱>.md`
（使用者指定位置優先）

## 範圍確認

如果設計涵蓋多個獨立子系統，應該在思考整理（`brainstorm`）階段就拆開了。如果沒有，建議拆成多份計畫——每份計畫獨立產出可驗證的成果。

## 先定義驗收標準

先定義「怎樣算做好」，再開始做。

原因：沒有先定義驗收標準，就不知道什麼時候該停下來，結果是做太多、做太少，或做了但做偏，時間花在排查和返工上。做完才補的標準會去配合已經做出來的東西，而不是需求，所以順序要是先定義、再動手。

下面的通用流程要照順序做完。原因是基線確認和事後驗證要成對，先確認「現在還沒達到」，之後的「達到了」才有意義。

### 適用時機

- **嚴謹任務**：每次都做。簡單任務的標準通常半分鐘就能列完，而簡單任務也最容易因為沒說出口的假設而做偏。
- **混合任務**：簡化版，不用寫計畫文件，至少列出「做完時我期望看到什麼」。
- **創意任務**：不適用（四不二要就是驗收標準）。

要省略驗收標準時，先取得使用者同意。做到什麼程度算完成是使用者的決定。

### 通用流程

動手之前：

1. 定義：做完時，成功長什麼樣？
2. 確認：現在還沒達到這個狀態（基線確認）
3. 動手
4. 驗證：現在達到了嗎？
5. 達到了才宣稱完成

這就是 TDD 的 Red-Green 循環泛化到所有任務類型。

定義標準時的判斷方式：

- **標準要寫到能判斷通過或不通過**。「品質要好」無法判斷，「pattern checklist 6 項全過」可以。做完之後發現「不確定算不算做好」，代表標準不夠具體，回到第 1 步補上。
- **沿用之前類似任務的標準時，對照這次的需求重新確認一遍**。類似的任務，需求常常差在細節。
- **發現自己已經動手但還沒定義標準時，停下來**。先依照需求把標準列出來（依照需求，不是依照已經做出來的東西），再從第 1 步重新走。

### 各任務類型的驗收標準

#### 程式開發（TDD）

經典的 Red-Green-Refactor：

1. **寫測試**（定義驗收標準）
2. **跑測試確認失敗**（基線確認）
3. **寫最小實作**（動手）
4. **跑測試確認通過**（驗證）
5. **重構**（打磨）

先寫測試，再寫產品程式碼。如果已經先寫了程式碼，把它刪掉，從測試重新開始。刪掉的程式碼不留著當參考，也不邊看邊補測試。看著既有程式碼寫出來的測試，測的是已經寫出來的東西，而不是需求要的東西，詳見下面的「為什麼順序重要」。

手動測過一次不能取代測試：手動測試沒有紀錄、不能重跑，涵蓋到哪些情況也是隨機的。

##### 好的測試

| 品質 | 好 | 壞 |
|------|---|---|
| **最小化** | 測一件事。名稱裡有「和」就該拆 | `test_驗證信箱和網域和空白` |
| **清楚** | 名稱描述行為 | `test_test1` |
| **意圖明確** | 展示期望的 API | 模糊了程式碼該做什麼 |

##### 為什麼順序重要

「先寫完再補測試」的問題：
- 測試立刻就通過了，但通過不代表它測對了東西
- 你會測你寫出來的東西，不是測需求要的東西
- 你會驗證你記得的邊界情況，不是你發現的
- 你從來沒看到測試抓到 bug

#### 教學影片

驗收標準 = pattern checklist + 技術品質：

**腳本階段：**
- [ ] TIER 0：不俯視觀眾 → 通過
- [ ] TIER 1 必勝 6 項：每項逐一確認
- [ ] TIER 2 加分 5 項：有多少算多少

**動畫階段：**
- [ ] 每張投影片視覺正確（截圖確認）
- [ ] 互動式圖表使用正確的工具（D3 / JSXGraph 等）
- [ ] 排版符合卡片規範（橫向讀取靠左置中、縱向讀取置中靠上）

**TTS 階段：**
- [ ] 發音正確（特別是專有名詞和數學符號）
- [ ] 斷句自然、語速適中
- [ ] 品質不低於基準（Puck F0）

**合成階段：**
- [ ] 音畫同步
- [ ] 字幕對齊
- [ ] 影片可正常播放

#### AI 算圖

驗收標準 = 評圖四面向：

- [ ] **合理性**：視覺元素是否服務於角色的故事
- [ ] **生命感**：角色像活的，不是擺拍的假人
- [ ] **技術面**：色調乾淨、皮膚自然、五官比例正常
- [ ] **細節面**：眼睛清晰、角色可辨識

如果要釋出：
- [ ] 不含社群成員的個資或暱稱（隱私紅線）
- [ ] prompt 沒有觸發 NSFW filter 的關鍵字

#### 研究 / 寫作

- [ ] 論點有證據支持
- [ ] 引用來源可查證
- [ ] 目標讀者能理解
- [ ] 沒有邏輯漏洞

#### 部署

- [ ] 服務可存取
- [ ] 環境變數正確
- [ ] .env 沒被打包進 tar
- [ ] docker 容器正常運作
- [ ] 備份存在且大小合理

### 定不出標準時

| 問題 | 解法 |
|------|------|
| 不知道怎麼定義驗收標準 | 問使用者「你期望做完時看到什麼？」 |
| 驗收標準太複雜 | 任務太大，拆小。 |
| 不確定標準是否合理 | 列出來讓使用者確認。 |

## 檔案盤點

動手之前，先列出所有會新增或修改的檔案，標明每個檔案的職責。這是分工拆解的基礎。

原則：
- 每個檔案有一個清楚的職責
- 一起變動的檔案放在一起
- 現有專案裡，先遵循既有風格
- 偏好小而聚焦的檔案——方便理解也方便編輯

## 先列可能會變的決定

計畫開頭、任務清單之前，先列出這份計畫裡最可能被使用者改掉的決定：技術選型、資料格式、介面長相、範圍取捨這類有其他合理選項、而且改了會牽動後面許多步驟的地方。每一項寫選了什麼、為什麼、改掉會影響哪些任務。

使用者審計畫的時間有限，建檔、跑測試、commit 這些機械性的步驟不需要逐條看。真正需要使用者判斷的決定如果埋在第七個任務裡，常常是做到那裡才發現要改，前面的工作就得重做。

- 判斷方式：問「這一項如果使用者說換一種，計畫要重寫多少？」要重寫很多的列進來。照既有慣例做、沒有其他合理選項的不用列。
- 任務的排列也照這個原則：在依賴關係允許的範圍內，把用來驗證這些決定的任務排前面，純機械的工作排後面。決定要改的時候，已經做掉的工作最少。
- 沒有這類決定的小計畫，寫一句「這份計畫沒有需要先確認的決定」即可。

## 步驟粒度

**每一步是一個動作（2-5 分鐘）：**

程式開發範例：
- 「寫測試」— 一步
- 「跑測試確認失敗」— 一步
- 「寫最小實作讓測試通過」— 一步
- 「跑測試確認通過」— 一步
- 「commit」— 一步

影片製作範例：
- 「撰寫大綱」— 一步
- 「擴展腳本」— 一步
- 「自審腳本品質」— 一步
- 「生成投影片」— 一步
- 「截圖檢查每張投影片」— 一步

算圖範例：
- 「確認 prompt 需求」— 一步
- 「選擇模型和 LoRA」— 一步
- 「生成初版」— 一步
- 「評圖檢查品質」— 一步
- 「調整 prompt 重生」— 一步

## 計畫文件格式

每份計畫以這個開頭：

```markdown
# [功能名稱] 實作計畫

> **給執行者：** 使用執行計畫（`execute`）skill 逐步完成此計畫。步驟使用 checkbox（`- [ ]`）格式追蹤進度。

**目標：** [一句話描述這份計畫要做出什麼]

**方法：** [2-3 句話描述做法]

**工具 / 技術：** [會用到的關鍵工具或技術]

**請先確認的決定：**
1. [決定]：選了 [做法]，因為 [原因]。改掉會影響任務 [編號]。

---
```

## 任務結構

### 程式開發任務

````markdown
### 任務 N：[元件名稱]

**檔案：**
- 新增：`精確/路徑/檔案.py`
- 修改：`精確/路徑/既有.py:123-145`
- 測試：`tests/精確/路徑/test_檔案.py`

- [ ] **步驟 1：寫測試**

```python
def test_具體行為():
    result = function(input)
    assert result == expected
```

- [ ] **步驟 2：跑測試確認失敗**

執行：`pytest tests/path/test.py::test_name -v`
預期：FAIL，訊息「function not defined」

- [ ] **步驟 3：寫最小實作**

```python
def function(input):
    return expected
```

- [ ] **步驟 4：跑測試確認通過**

執行：`pytest tests/path/test.py::test_name -v`
預期：PASS

- [ ] **步驟 5：commit**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: 新增某功能"
```
````

### 影片製作任務

````markdown
### 任務 N：[階段名稱]

**檔案：**
- 輸入：`精確/路徑/input.json`
- 輸出：`精確/路徑/output/`
- 設定：`精確/路徑/config.py`

- [ ] **步驟 1：觸發 pipeline**

操作：在平台管理頁面點擊「生成此主題」
預期：alert 顯示「成功觸發: 1」

- [ ] **步驟 2：監控進度**

操作：開啟 Monitor 監控 docker logs
預期事件序列：Router → Outline → Script → Consultant → Improve → Review → Pipeline complete

- [ ] **步驟 3：品質自審**

操作：下載輸出檔案，逐一檢查
驗收標準：
- 腳本 pattern checklist 6/6
- 投影片無視覺瑕疵
- TTS 發音正確、斷句自然
````

### 通用任務

````markdown
### 任務 N：[步驟名稱]

**輸入：** [需要什麼才能開始]
**輸出：** [做完會產出什麼]

- [ ] **步驟 1：[動作]**

操作：[具體怎麼做]
預期：[做完會看到什麼]

- [ ] **步驟 2：[驗證]**

操作：[怎麼確認做對了]
預期：[正確的結果長什麼樣]
````

## 佔位符

每一步都要包含執行者需要的實際內容，因為執行者對這個專案一無所知，計畫沒寫到的地方只能用猜的。下面這些寫法都是佔位符，換成實際內容：

- 「待定」「TODO」「之後再說」「之後補」
- 「加上適當的錯誤處理」「做好驗證」「處理邊界情況」
- 「針對上面的內容寫測試」（沒附測試程式碼）
- 「跟任務 N 類似」（重複寫一遍——執行者可能不按順序讀）
- 只描述「做什麼」但沒有「怎麼做」的步驟
- 引用了沒有在任何任務中定義的型別、函式、方法

## 自審

寫完計畫後，用新的眼光檢查一遍：

1. **設計覆蓋度**：翻一遍設計文件的每個需求，每個都能對應到計畫中的某個任務嗎？列出缺口。
2. **佔位符掃描**：搜尋上面「佔位符」一節列出的模式。修掉。
3. **一致性**：後面的任務用到的型別、函式名稱跟前面定義的一樣嗎？任務 3 叫 `clearLayers()`、任務 7 叫 `clearFullLayers()` 就是 bug。
4. **決定前置**：有其他合理選項、改了會牽動許多步驟的決定，都列在計畫開頭了嗎？

有問題直接修，不用重跑自審。如果發現設計有需求但計畫沒涵蓋，補上任務。

## 執行交接

計畫存檔後，提供執行選項：

> **「計畫寫好了，存在 `<路徑>`。兩種執行方式：**
>
> **1. 子代理執行（推薦）** — 每個任務派一個獨立子代理，任務間做 review
>
> **2. 本 session 執行** — 在目前的對話中逐步執行，設定 review 檢查點
>
> **你選哪個？」**

選擇後觸發執行計畫（`execute`）skill。

## 和其他 skill 的關係

- **思考整理**（`brainstorm`）：探索階段可能產出初步的驗收標準，在這裡定案。
- **執行計畫**（`execute`）：照計畫逐步做，每個任務的驗證步驟就是驗收標準的具體化。
- **完成驗證**（`verify`）：宣稱完成前，用這裡定的驗收標準做最後驗證。

## 核心提醒

- 精確的檔案路徑
- 每個步驟都附具體內容——程式碼步驟要有程式碼，操作步驟要有操作指令
- 驗證步驟要寫預期輸出
- DRY、YAGNI、先定義驗收標準再實作
