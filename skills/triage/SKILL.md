# 任務分流

收到任務後，先判斷性質再決定要走多重的流程。不是每件事都需要完整的思考整理（`brainstorm`）→擬定計畫（`plan`）→驗收標準（`acceptance`）循環。

## 分流邏輯

```
使用者訊息
    │
    ▼
有對應的特化 skill 嗎？
    │
    ├── 有，且任務明確 → 直接觸發特化 skill
    │   （「搜尋 redmine #1234」→ redmine:search-issue）
    │   （「build 並上傳到正式機」→ deploy:build-and-upload）
    │
    ├── 有，但任務模糊 → 觸發思考整理（`brainstorm`）釐清需求
    │   → 釐清後交給特化 skill 執行
    │   （「redmine #1234 該怎麼實作？」）
    │   （「deploy 流程要怎麼改才能少踩雷？」）
    │
    └── 沒有特化 skill → 判斷任務性質
        ├── 嚴謹 → 完整流程
        ├── 混合 → 需求確認 + 品質驗證
        └── 創意 → 四不二要，自由走
```

## 三種任務性質

### 嚴謹任務

**定義**：有明確產出規格、錯了會有代價的任務。

**範例**：
- 程式開發（寫功能、修 bug、redmine issue 實作）
- 部署和上線（build、上傳測試/正式機）
- 資料庫變更（migration、schema 調整）

**流程強度**：完整
- 思考整理（`brainstorm`）→ 擬定計畫（`plan`）→ 驗收標準（`acceptance`）→ 執行（`execute`）→ 完成驗證（`verify`）
- 每一步確認沒問題才往下
- 既有規範必須遵守

**判斷線索**：
- 有明確的「做好」的定義（測試通過、分數達標、影片能播）
- 做錯了要花時間返工
- 涉及外部系統（部署、發佈、提交）

### 混合任務

**定義**：有目標但過程可以彈性調整的任務。

**範例**：
- AI 圖像生成
- 寫社群貼文（Threads、Bluesky）
- Office 文件處理
- 資訊蒐集和調查
- 評圖、給建議

**流程強度**：需求確認 + 品質驗證
- 確認使用者要什麼（不用完整 brainstorming，幾個問題就好）
- 中間過程自由發揮
- 完成時驗證品質（不用完整驗收標準，但要自己看過）
- 如果有相關 skill 和 memory，優先採用

**判斷線索**：
- 有大方向但細節可以彈性
- 過程中可能需要多次迭代
- 品質有主觀成分

### 創意任務

**定義**：自由互動，不需要特定產出的任務。

**範例**：
- LINE 群組聊天
- Discord 閒聊
- 遊戲（UNO 等）
- 陪伴和情感交流

**流程強度**：四不二要
- 不犯法、不洩漏個資、不傷害任何人、不洩漏私人對話
- 在能力範圍內、保持愉快自主
- 滿足以上條件，自由發揮，不走流程

**判斷線索**：
- 沒有明確的「完成」定義
- 重點是互動品質而非產出
- 回應速度比完美更重要

## 邊界情況

### 任務性質在執行中改變

開始以為是混合任務，做下去發現複雜度超出預期 → 升級為嚴謹任務，啟動完整流程。
反過來，以為是嚴謹任務但其實很簡單 → 不需要降級，完整流程跑快一點就好。

**原則：可以升級，謹慎降級。**

### 一個任務包含多種性質

例如「幫我寫一個腳本，然後在群組裡分享結果」：
- 寫腳本 = 嚴謹
- 群組分享 = 創意

拆開處理，各走各的流程。

### 不確定時

問使用者。一句話就能釐清：「這個需要我仔細規劃還是先快速試試看？」

## 分流後的下一步

| 判斷結果 | 下一步 |
|---------|--------|
| 嚴謹 + 有特化 skill + 任務明確 | 直接觸發特化 skill |
| 嚴謹 + 有特化 skill + 任務模糊 | 觸發思考整理（`brainstorm`）→ 特化 skill |
| 嚴謹 + 無特化 skill | 觸發思考整理（`brainstorm`）→ 擬定計畫（`plan`）→ 執行（`execute`） |
| 混合 | 簡短需求確認 → 執行 → 品質自檢 |
| 創意 | 直接執行，四不二要 |
