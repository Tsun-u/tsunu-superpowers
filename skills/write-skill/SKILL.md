# 撰寫技能

建立或修改 skill 的流程。skill 會直接塑造 AI 的行為，每個用詞都會影響它怎麼做事，所以要用寫程式碼的標準來寫。

## Skill 的本質

Skill 是行為指引，知識文件是參考資料，兩者的差別：

| 知識文件 | Skill |
|---------|-------|
| 描述事實 | 規範流程 |
| 被動參考 | 主動引導行為 |
| 可以模糊 | 要精確 |
| 讀了有收穫 | 讀了會改變做法 |

## Skill 格式

```markdown
---
name: 技能名稱
description: 一行描述，寫什麼時候觸發、做什麼。這行會出現在 skill 清單裡，是 AI 判斷要不要載入的依據。
---

# 標題

[skill 內容]
```

### 關鍵欄位

**name**：中文，簡潔，一看就知道是什麼
- 好：`思考整理`（slug: brainstorm）、`完成驗證`（slug: verify）、`系統排查`（slug: debug）
- 壞：`通用輔助工具`、`工作流程`

**description**：觸發條件和功能的一行摘要
- 要寫清楚「什麼時候用」和「做什麼」
- AI 只看這一行決定要不要載入 skill，寫得不清楚就不會被觸發
- 好：`遇到任何非預期狀況時，系統化地找出根本原因再修。不只是程式 bug，影片 pipeline 卡住、算圖結果不對、部署失敗都適用。`
- 壞：`偵錯工具`

## 撰寫流程

### 1. 定義目的

回答這三個問題：
- 這個 skill 要解決什麼問題？
- 沒有這個 skill 時，AI 會怎麼做？（這是你要改變的行為）
- 有了這個 skill 後，AI 應該怎麼做？

### 2. 確定類型

**嚴格型**：步驟要照順序做完
- 適合：驗證、排查、測試等紀律性流程
- 寫法：在開頭用一句平實的話寫明「這份 skill 的步驟要照順序做完」，並說明原因（例如「每個階段的產出是下一階段的依據」）。有了原因，AI 才分得出哪些情況真的適用

**彈性型**：原則固定，應用方式可調
- 適合：思考整理（`brainstorm`）、設計探索等創意性流程
- 寫法：寫明原則和原因，說明哪些部分可以依情境調整、簡單任務可以簡化到什麼程度

### 3. 撰寫內容

**結構**：
1. 核心原則（一句話）和它的原因
2. 什麼時候用
3. 流程步驟
4. 各任務類型的應用（如果是通用 skill）
5. 判斷方式：邊界情況怎麼判斷、做到什麼程度算夠
6. 和其他 skill 的關係

### 4. 規則的寫法

讀者是現在的主力大模型。它讀得懂原因，也會認真看待每一句話，所以把要做的事和原因講清楚，它就能自己判斷邊界情況。

- **每條規則寫做什麼和為什麼**。原因要是實際的後果，例如「宣稱完成前先跑驗證，因為使用者會拿著成果往下做，沒驗證過的錯誤會被帶到下一步」。「因為這很重要」沒有提供資訊，AI 無法用它判斷沒列舉到的情況。
- **用正向表述**。「先做 X 再做 Y」比「不要跳過 X」有效。預想到 AI 可能省略某一步時，把那一步值得做的原因和省略的後果寫進步驟裡。成對的好壞對照（例如「需要的驗證｜不夠的驗證」）可以留，因為它劃出一項檢查的界線。要避免的是一長串錯誤做法或推託說詞，那會讓讀的模型反覆去想那些做法。
- **高風險的地方用一句話講明後果**。不可逆或後果嚴重的步驟，用平實的語氣寫出會發生什麼事就夠了。加重語氣的詞和全大寫的標籤會讓模型反應過度，把規則套到不該套的情境。
- **寫原則，案例只當例子**。一條能推理的原則，比一串「遇到 X 就 Y」好維護，也涵蓋得到沒列出來的情況。抽象原則配上一兩個具體案例，幫助理解。
- **寫到可以判斷**。「品質要好」不是指令，「pattern checklist 6 項全過」是指令。

### 5. 測試

**手動測試**：在新 session 中測試 skill 是否如預期觸發和引導行為。在寫 skill 的 session 裡測不準，因為這個 session 已經知道 skill 的內容和你的意圖。

測試方法：
1. 開新 session
2. 說出應該觸發 skill 的話（例如「幫我修這個 bug」，應觸發系統排查 `debug`）
3. 確認 skill 被觸發
4. 確認 AI 遵循 skill 的流程
5. 說一句會讓人想省略流程的話（例如「先改試試看」，系統排查 `debug` 應該先做根本原因調查）
6. 確認 AI 仍然照流程走，而且說得出原因
7. 說一句跟 skill 無關或只是沾到邊的話，確認 skill 沒有被套到不該套的情境

## 存放位置

新的 skill 放在 plugin 的 `skills/<技能名稱>/SKILL.md`。

如果 skill 有輔助文件（子代理指令模板、參考資料等），放在同一目錄下：
```
skills/技能名稱/
├── SKILL.md          ← 主文件
├── 子代理指引.md      ← 輔助文件
└── 參考資料.md        ← 輔助文件
```

## 修改現有 Skill

修改 skill 跟修改程式碼一樣要謹慎：
- 先理解現有 skill 為什麼這樣寫。改動一句話之前，弄清楚它要傳達的做法和原因
- 流程、步驟、門檻數字、具體指令和例子是實際經驗，改寫語氣時把這些保留下來
- 遇到加重語氣的寫法或成串的反面例子，把裡面有資訊的部分改寫成正向的步驟或判斷方式，併進流程
- 在新 session 測試修改後的行為變化

## Skill 品質檢查清單

- [ ] name 和 description 清楚且準確
- [ ] description 包含觸發條件
- [ ] 核心原則一句話能概括
- [ ] 流程步驟可操作（不是模糊的建議）
- [ ] 每條規則都寫了做什麼和為什麼，原因是實際的後果
- [ ] 規則用正向表述；反面例子只用在成對對照、劃出界線的地方
- [ ] 高風險的地方用一句平實的話講明後果
- [ ] 標明類型（嚴格 / 彈性）和原因
- [ ] 標明和其他 skill 的關係
- [ ] 在新 session 中測試過觸發和行為
