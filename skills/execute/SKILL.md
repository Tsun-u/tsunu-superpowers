# 執行計畫

讀取計畫、批判性審閱、選擇執行模式、逐步執行、完成後報告。

## 四種執行模式

計畫完成後，根據任務特性選擇合適的執行模式：

```
計畫審閱完畢 → 選擇執行模式
    │
    ├── 任務簡單 / 高度依賴 → 本 session 逐步
    │
    ├── 任務獨立 / 需要乾淨 context → 子代理
    │
    ├── 需要其他 session 的資源或專長 → switchboard 委派
    │
    └── 多個獨立任務可同時做 → 混合並行
```

### 模式一：本 session 逐步

在目前的對話中逐步執行，設定 review 檢查點。

**適用於**：
- 任務之間有高度依賴
- 需要使用者密切參與
- 簡單的計畫不值得派子代理

**流程**：
```
讀計畫 → 審閱 → 逐步執行（每 2-3 個任務暫停 review）→ 交付收尾（`deliver`）
```

### 模式二：子代理

每個任務派一個獨立子代理，任務間由主 session 做 review。

**適用於**：
- 任務獨立，不需要共享狀態
- 任務可以在同一個工作目錄完成
- 想要每個任務有乾淨的 context

**流程**：
```
主 session 讀計畫 → 審閱
    │
    ▼
任務 1 → 派子代理 → 收結果 → review → 通過？
    │                                    ├── 是 → 任務 2
    │                                    └── 否 → 修正後重試
    ▼
全部完成 → 觸發交付收尾（`deliver`）
```

**子代理指令模板**：
```markdown
執行以下計畫中的任務 N。

## 任務內容
[從計畫中複製完整任務]

## 工作目錄
[專案路徑]

## 重要規則
- 嚴格遵循步驟，不要跳步
- 每步做完跑驗證
- 卡住就回報，不要猜
- 不要做計畫以外的事

回報：完成了什麼、驗證結果、遇到什麼問題。
```

### 模式三：switchboard 委派

透過 switchboard 將任務委派給其他線上的 agent session。

**適用於**：
- 任務需要其他 session 正在使用的資源（Chrome MCP、GCE 等）
- 已有專責 session 在處理相關主題
- 任務需要不同的專長或視角

**前提**：目標 session 在線上且不忙（先查 SWITCHBOARD_STATUS.md）。

**流程**：
```
確認目標 session 在線 → 委派任務 → 等待回報 → review 結果 → 繼續
```

**委派規範**：遵循夥伴協作（`collaborate`）skill 的規範——

1. **任務描述**：要做什麼，一兩句話
2. **期望產出**：做完後要交付什麼
3. **參考資料**：相關檔案的路徑（不把內容貼過去）
4. **完成後回報**：做完通知誰、更新什麼紀錄

**委派範例**：
```
請幫我為 issue #1234 起草一份技術選型 ADR：評估快取方案 Redis 與 Memcached 的取捨。
期望產出：ADR 草稿，包含選項評估（功能/成本/相容性）、決策、後果。
參考資料：issue #1234 的需求討論串
完成後：結果 send 回給我（`main`），
同時在團隊知識庫對應資料夾建立該 ADR 文件。
```

（知識庫上載判準等規範詳見「夥伴協作」skill）

**不好的委派**：
- 「幫我看一下 issue #1234」— 太模糊
- 把整份檔案內容貼在訊息裡 — 浪費 token，給路徑
- 沒說完成後怎麼處理 — 做完了沒人知道

### 模式四：混合並行

多個獨立任務同時執行，混合使用子代理和 switchboard 委派。

**適用於**：
- 計畫中有多個彼此獨立的任務
- 部分任務可在本 session 用子代理做，部分需要委派
- 批次處理多個獨立項目

**判斷是否適合並行**：
```
多個任務？
    │
    ├── 彼此獨立嗎？
    │   ├── 否（有關聯）→ 依序執行
    │   └── 是
    │       ├── 會互相干擾嗎？（改同檔案、用同資源）
    │       │   ├── 是 → 依序執行
    │       │   └── 否 → 可以並行
    │       │       ├── 不需要特殊資源 → 子代理並行
    │       │       ├── 需要其他 session 資源 → switchboard
    │       │       └── 混合需求 → 子代理 + switchboard 混合
```

**流程**：
```
分析任務依賴關係 → 分組
    │
    ├── 獨立任務群 A → 子代理 1 + 子代理 2（並行）
    ├── 獨立任務群 B → switchboard 委派 session X
    └── 依賴任務 C → 等 A、B 完成後再做
    
全部回來 → 檢查衝突 → 整合 → review
```

**並行時的注意事項**：
- 子代理用同一個 Agent tool 呼叫中發出多個，才會真正並行
- switchboard 委派前確認目標 session 在線且不忙
- 同時不要委派太多給同一個 session
- 追蹤哪些已回覆、哪些還在等

**收結果後**：
1. 看每個摘要——理解做了什麼
2. 檢查衝突——有沒有改到同一段程式碼或檔案
3. 跑完整驗證——合在一起沒問題
4. 抽查——代理或其他 session 可能有系統性錯誤

## 執行流程（所有模式通用）

### 第一步：讀取並審閱計畫

1. 讀計畫文件
2. 批判性審閱——找出任何疑問或疑慮
3. 有疑慮 → 跟使用者確認再開始
4. 沒有疑慮 → 建立任務追蹤，開始執行

### 第二步：選擇模式

根據任務特性和可用資源，從四種模式中選擇。複雜計畫可能在不同任務用不同模式。

提供選項讓使用者確認：

> **「計畫審閱完畢。建議的執行方式：**
>
> - 任務 1-3：子代理（獨立且可在本 session 完成）
> - 任務 4：switchboard 委派 batch session（需要特定資源）
> - 任務 5：等 1-4 完成後本 session 執行（有依賴）
>
> **你覺得這樣安排如何？」**

### 第三步：逐任務執行

每個任務：
1. 標記為「進行中」
2. 按步驟嚴格執行（計畫裡的步驟都已經拆到最小了）
3. 跑計畫指定的驗證
4. 驗證通過 → 標記「完成」
5. 驗證失敗 → 停下來，不要硬做

### 第四步：完成

所有任務完成並驗證後 → 觸發交付收尾（`deliver`）skill。

## 什麼時候該停下來

**立刻停止執行：**
- 碰到阻塞（缺少依賴、驗證失敗、指示不清楚）
- 計畫有重大缺漏，無法繼續
- 不理解某個指示的意思
- 驗證反覆失敗
- switchboard 委派無回應且超時

**問清楚再繼續，不要猜。**

## 什麼時候該回到審閱

- 使用者根據回饋更新了計畫
- 根本性做法需要重新思考

## Review 檢查點

### 子代理 / switchboard 委派

每個代理或 session 完成後，主 session 做 review：

1. **看產出**：做了什麼改動 / 產出了什麼
2. **跑驗證**：獨立驗證結果（不要只信回報）
3. **跟計畫對照**：做的跟計畫一致嗎
4. **品質檢查**：有沒有引入新問題

### 本 session 模式

每 2-3 個任務暫停一次，做同樣的 review。

### 混合並行

所有並行任務回來後，額外做一輪整合 review：
- 並行產出之間有沒有衝突
- 合在一起後整體是否一致

## 核心提醒

- 批判性審閱計畫再開始
- 選擇合適的執行模式（不是永遠用同一種）
- 嚴格遵循計畫步驟
- 不跳過驗證
- 卡住就停，不要猜
- 子代理和 switchboard 的回報都需要獨立驗證
- switchboard 委派遵循夥伴協作（`collaborate`）skill 的規範
