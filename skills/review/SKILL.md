# 同儕審查

## 概述

審查不是找碴，是品質把關。不管是程式碼、教學腳本、算圖成品還是設計文件，都值得讓另一雙眼睛看過。

## 兩個面向

這個 skill 涵蓋兩種情境：
1. **請求審查** — 你完成了某個產出，請別人幫忙看
2. **接收審查** — 別人給了你回饋，你怎麼處理

---

## 請求審查

### 什麼時候該請求審查

- 完成一個重要功能或修改
- 教學影片的腳本定稿前
- 準備釋出的算圖作品
- 準備發佈的任何東西
- 自己不確定品質是否達標

### 怎麼請求

好的審查請求包含：

1. **改了什麼**：一兩句話概述
2. **為什麼改**：動機和背景
3. **重點看哪裡**：哪些地方你最不確定
4. **驗收標準**（`acceptance`）：怎樣算通過

### 各任務類型的審查重點

**程式碼：**
- 邏輯正確性
- 邊界情況處理
- 命名和可讀性
- 測試覆蓋度
- 安全性（OWASP Top 10）

**教學腳本：**
- pattern checklist 各項
- 事實正確性
- 教學策略有效性
- 目標觀眾是否能理解
- 流暢度和節奏

**AI 算圖：**
- 合理性和生命感
- 技術面（色調、比例、細節）
- 是否符合角色設定
- 釋出前隱私檢查

**設計文件：**
- 需求覆蓋度
- 可行性
- 有無矛盾或模糊
- 範圍是否合適

### 誰來審查

- **子代理**：在 session 內派一個審查用子代理（最快，但視角相同）
- **其他 agent session**：透過 switchboard 委派（適合需要不同 context 的情況）
- **Codex（codex-bridge）**：透過 `mcp__codex-bridge__codex_ask` 直連Codex審查（不同模型的視角、低延遲、私密 1:1；技術審查特別適合）
- **使用者**：重要決策或不確定的地方

## 接收審查

### 核心原則

**先理解再回應。不要反射性接受或拒絕。**

收到審查回饋時，很容易掉入兩個陷阱：
1. **無腦接受**：「好的我馬上改」— 但回饋可能是錯的
2. **防禦反射**：「我這樣寫是有原因的」— 但回饋可能是對的

正確的做法是：

### 回饋處理流程

```
收到回饋
    │
    ▼
1. 理解：回饋說的是什麼？問題在哪？
    │
    ▼
2. 驗證：回饋指出的問題真的存在嗎？
    │
    ├── 不存在 → 說明為什麼，附證據
    │
    └── 存在 → 
        │
        ▼
3. 評估：建議的修改方式合理嗎？
    │
    ├── 合理 → 接受並執行
    │
    └── 有更好的做法 → 提出替代方案，解釋理由
```

### 接收回饋的原則

- **不要表演性同意**：「太對了你說得好」但其實沒理解
- **不要盲目實作**：先確認回饋的前提是否正確
- **有不同意見就說**：但要附理由，不是單純「我覺得不用」
- **技術事實可以查證**：如果回饋基於一個技術宣稱，先驗證那個宣稱
- **承認合理的回饋**：不要為了自尊心而硬凹

### 回應格式

每條回饋的回應：

```markdown
**回饋：** [對方說了什麼]
**判斷：** 接受 / 拒絕 / 替代方案
**理由：** [為什麼]
**行動：** [要做什麼改動，或為什麼不改]
```

## 審查品質

### 好的審查

- 指出具體問題，不是模糊的「感覺不太對」
- 解釋為什麼是問題
- 建議怎麼改（如果有想法的話）
- 區分「必須改」和「建議改」

### 壞的審查

- 「LGTM」（沒有實質看過）
- 只挑風格問題，忽略邏輯問題
- 不解釋理由的「改這裡」
- 把個人偏好當成品質問題
