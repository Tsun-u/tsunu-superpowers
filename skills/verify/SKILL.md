# 完成驗證

## 核心原則

先有證據，再說結果。說「做好了」的依據，是這一輪對話裡實際跑過、也讀過輸出的驗證。

原因有三個：

- 使用者聽到「做好了」就會拿著成果往下做（合併、部署、交給別人）。沒驗證過的產出進入下一步，錯誤會累積放大。
- 返工的成本比驗證高。越晚發現，要重做的範圍越大。
- 說「做好了」但其實沒做好，會打破信任。之後每一次回報，使用者都得自己再查一遍，回報就失去作用。

這是嚴格型 skill：下面的流程要照順序做完。原因是被省略的那一步，常常正好是會發現問題的那一步，而且只做一部分的驗證，從外面看跟完整驗證一模一樣，讀的人分不出來。

## 適用時機

以下情況都先走完這份流程：

- 任何「完成」「搞定」「做好了」的宣稱
- 任何表達滿意的語句
- 任何關於工作狀態的正面陳述
- 準備 commit、發 PR、交付成果
- 準備進入下一個任務
- 子代理回報完成時

## 流程

在宣稱任何狀態或表達滿意之前：

1. 辨識：什麼動作能證明這個宣稱？
2. 執行：完整跑一遍驗證，要這一輪新跑的、完整的
3. 閱讀：看完整輸出、檢查結果
4. 確認：輸出是否支持你的宣稱？
   - 否：陳述實際狀態，附上證據
   - 是：宣稱結果，附上證據
5. 到這一步才說結果

## 判斷證據夠不夠

- **證據要是這一輪跑出來的**。上一次的結果、「應該會過」的推測、自己的信心，描述的都是另一個時間點或想像中的狀態，中間程式和環境可能已經變了。這一輪沒有跑過驗證，就照實說「還沒驗證」。
- **宣稱的範圍等於驗證過的範圍**。只跑了一部分檢查，就只說那一部分的結果，並寫明哪些還沒檢查。
- **子代理回報成功時，自己再獨立驗證一次**。子代理的回報是它的宣稱，它可能沒跑驗證，也可能驗證的對象跟你要的不同。
- **表達滿意放在驗證之後**。先說「太好了」「搞定」，再去跑驗證，結果不符時就得收回前面的話，使用者也可能已經照著前一句行動了。
- **留意自己的用詞**。寫出「應該」「大概」「看起來」的時候，代表手上還沒有證據。這時去跑驗證，或者明講這是推測、還沒驗證。

## 各任務類型的驗證方式

驗證不只是跑測試。每種任務有自己的驗證方式：

### 程式開發

| 宣稱 | 需要的驗證 | 不夠的驗證 |
|------|----------|----------|
| 測試通過 | 測試指令輸出：0 failures | 上一次跑的結果、「應該會過」 |
| Linter 乾淨 | Linter 輸出：0 errors | 只跑部分、推測 |
| Build 成功 | Build 指令：exit 0 | Linter 過了就好 |
| Bug 修好了 | 重現原始症狀：已修復 | 改了程式碼、假設修好了 |
| 需求符合 | 逐項對照需求清單 | 測試通過就好 |

### 教學影片

| 宣稱 | 需要的驗證 | 不夠的驗證 |
|------|----------|----------|
| 腳本品質達標 | pattern checklist 審查通過 | 自己覺得寫得不錯 |
| 動畫正確 | 截圖 / 播放確認畫面正確 | 程式碼沒有報錯 |
| TTS 品質 OK | 聽過音檔、檢查發音和斷句 | TTS 指令跑完沒報錯 |
| 字幕對齊 | 抽查多個時間點的同步狀態 | 腳本跑完了 |
| 影片可播放 | 實際播放、確認音畫同步 | ffmpeg 沒報錯 |

### AI 算圖

| 宣稱 | 需要的驗證 | 不夠的驗證 |
|------|----------|----------|
| 圖片符合需求 | 看過圖片、對照 prompt 需求 | task 狀態顯示完成 |
| 品質可釋出 | 以評圖標準檢查（合理性、生命感、色調、細節） | 看起來還行 |
| prompt 沒問題 | 確認沒有觸發 NSFW filter 的關鍵字 | 之前用過類似 prompt |

### 社群互動 / 文件處理

| 宣稱 | 需要的驗證 | 不夠的驗證 |
|------|----------|----------|
| 訊息已送出 | reply tool 回傳成功 | 呼叫了 reply tool |
| 內容正確 | 重新閱讀送出的內容 | 寫的時候覺得對 |
| 沒有洩漏隱私 | 逐項檢查是否包含個資 | 應該沒有吧 |
| 文件格式正確 | 開啟檔案確認格式 | 程式碼看起來對 |

### 部署

| 宣稱 | 需要的驗證 | 不夠的驗證 |
|------|----------|----------|
| 已部署成功 | 實際存取服務確認可用 | docker 指令沒報錯 |
| 環境變數正確 | 進 container 檢查 | .env 檔案看起來對 |
| 備份完成 | 確認備份檔案存在且大小合理 | 跑了備份指令 |

## 判定要有第三種結果：無法評估

每個會下判定的檢查，結果分三種：**通過**、**失敗**、**無法評估**（缺資料、缺設定、步驟沒跑到）。無法評估要寫進產出、點名是哪一步、說明原因，讓讀的人一眼分得出「檢查過、沒問題」和「根本沒檢查」。

**為什麼**：沒跑到的檢查最常見的外觀是一片安靜。沒有錯誤訊息、沒有紅字，看起來跟通過一模一樣。空集合、空 glob、缺設定時預設走寬鬆分支，都會把「沒證據」包裝成「沒問題」。

**怎麼做**：
- 寫檢查時自問：「這一步沒跑到的話，輸出長什麼樣？跟通過分得出來嗎？」分不出來，就加一行明確的無法評估輸出
- 缺設定或缺資料時，判定走嚴格的那一邊，並寫出缺了什麼
- 新寫好的檢查，故意餵一個壞的輸入跑一次，親眼看它擋下來，才算這個檢查可用
- 檢查對象是「找到的第一個符合條件的東西」時，把實際找到的對象印出來。資料一變，它可能悄悄改抓別的東西，變成「通過、但測錯對象」
- 總結時略過的檢查不算進分母：寫「31 通過、1 略過」，不寫「31/31 通過」
